# 文案回稿后，怎样做给玩家的试玩

## 先区分现在和之后

现在完成的是当前开发样本的操作修复、答案兼容和图文需求清单。最终新文章、用户绘制素材、八个站点的完整新内容还没有收到或制作，不能把资料清单当作已实现的网站。

第一批玩家试玩先验证一条完整调查链。其他完整站点按 P1/P2 回稿再接入，不用一开始把所有图与全文都交齐。暂未开放的内容不做假入口，不在开场显示全体程序和人物。

## 接到稿件后做什么

1. **先对稿。** 按内容 ID 对齐标题、作者、日期、店名与人名；检查 2006/2023/2026 和 2008 硬件年代。看到新角色或结局关键事实时先标出与原稿的差异，不自作主张补另一个版本。
2. **确认线索公平。** 真正有用的词必须出现在玩家可读正文中，下一份资料确实能用这个词搜出。普通文章保留，不自动把关键词高亮成任务卡。
3. **接入正文与检索。** 用同一份数据驱动阅读页、索引与历史，保留文章来源和回看位置；私人邮件只用合理的本机索引。
4. **接入填写容错。** 根据写手答案表更新每框的 2–3 个以上别名，忽略标点与大小写；不增回原文勾选，不请 AI 批改谜题。
5. **接入画。** 按素材 ID 和最终宽高替换占位，保留像素比例。日期、图注、门牌与 UI 继续由代码叠加。没画好的仍写“需要画”。
6. **接剧情。** 成功后自动切回固定 GG 消息，关键长文不按秒数打断。结尾附件可读、能回看；自由 AI 聊天与固定剧情的权限分开。
7. **跑完整链再发。** 中英文、桌面和手机、刷新、回看、错误答案、短答案和旧样本进度全部实际操作。出现阻塞先修，不给测试玩家一串尚未验证的下一步说明。

## 第一批试玩实际路线

**GG 的消息 → 拍照备忘 → 周刊周年报道 → 自己搜店名 → 小店专访或商户目录 → 搜人名 → 邮件 → 三框填写 → 自动收到新消息 → 照片背面与下一章疑问。**

日记和镇民来信可以随便读，也可以不读。需要观察搜索与填写的玩家不会被无关内容锁住。第一段不放 NULL 闪屏，不用大量 Jump Scare 代替故事。试玩结束显示明确的“本次试玩到这里”，避免被误认为游戏出错；正式完整游戏的结尾才使用 GAME OVER。

## 想从玩家那里知道什么

| 问题 | 具体观察 |
| --- | --- |
| 开场能否理解为什么找楚人？ | 玩家是否知道 GG 是朋友、电脑只是新线索，不是接到一份酒店工作 |
| 是否愿意读文章？ | 哪段想跳、哪里像假文章、有没有愿意读的普通生活内容 |
| 能否自己想到新搜索词？ | 在哪句话找到店名/人名；卡住是线索不清还是不懂搜索功能 |
| 填写是否顺手？ | 记录原样答案；意思正确却不通过时补别名，不要求玩家照标准句抄 |
| 下一步是否清楚？ | 解完后是否看到 GG 新消息；返回原文是否保留位置 |
| 是否开始在乎楚人？ | 能否记起他的一个生活细节，而不仅记得酒店和编号 |

玩家测试不默认上传聊天或存档，不接入额外统计服务。反馈由玩家自愿提供；开发检查记录步骤与问题即可。现有在线 AI 继续遵守原启用同意机制。

## 发布边界

开发预览继续独立于正式游戏。收到正文后可以先做一条稳定的试玩链接；正式入口是否切到 2.1，等完整内容与玩家测试结果再决定。本次不更新 main，也不把现有微信、B-3 或旧结局删掉来给新壳让路。
